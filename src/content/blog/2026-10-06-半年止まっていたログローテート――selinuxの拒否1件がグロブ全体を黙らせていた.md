## はじめに

2026年10月4日、本番VPS（CentOS Stream 9、KUSANAGI）でnginxの停止を調べていたときのことです。error.logを遡ると、毎晩00:00に同じ行が出ていました。

```text
open() ".../log/nginx/access.log" failed (13: Permission denied)
```

過去のerror.logがどれも00:00付で残っていたのは、これが原因でした。追っていくと問題は2層ありました。1つはログディレクトリの権限、もう1つはSELinuxによるlogrotateの拒否です。後者のせいで、ログは半年以上ローテートされていませんでした。

本記事では、`missingok` と成功終了が失敗を隠す構造、「手動では動くのに夜間だけ動かない」実行コンテキストの差、そしてラベルの管理方法の見直しを扱います。プロファイル名・ドメイン・ユーザー名は汎用化し、「WordPressのプロファイル」「別CMSのプロファイル」と呼びます。

## 背景・課題

構成は次のとおりです。

- nginxはマスタープロセスがroot、ワーカープロセスが一般ユーザーで動く
- ログは `/home/kusanagi/<プロファイル>/log/nginx/` に置かれ、logrotateの設定は `/home/kusanagi/*/log/nginx/*.log` というグロブ（ワイルドカードによるパス指定）で全プロファイルをまとめて対象にする
- postrotateスクリプトでマスターにUSR1を送り、ログを開き直させる

nginxの公式ドキュメントによれば、USR1を受けたマスターはログを開き直してワーカーの一般ユーザーを所有者に設定し、その後ワーカーも新しいファイルを開き直します（nginx, 2026）。つまり、ワーカーのユーザーがログディレクトリに入れないと、開き直しの段階で失敗します。

厄介なのは、どちらの問題も「何も起きていない」ように見えることでした。logrotate.serviceは毎晩「Deactivated successfully」で終わり、エラーメールもありません。

## 本論

### 権限の層：開き直しだけが失敗する

`log/` と `log/nginx` は `root:root` の754でした。その他（other）に実行権（x）が無いので、ワーカーのユーザーはディレクトリに入れません。起動時はroot権限のマスターがログを開くので普段は書けています。失敗するのはUSR1による開き直しのときだけで、それが00:00のエラーの正体でした。正常に見える別のプロファイルに合わせて755に直しました。

調査の途中でつまずいた点も1つあります。`sudo ls /home/kusanagi/*/log/nginx` が「そのようなファイルはない」と返ったのです。グロブはsudoの外、つまり一般ユーザーの権限でシェルが展開します。一致するものが無ければ、bashは語をそのまま残します（GNU Project, 2025）。lsにはパターンの文字列がそのまま渡り、そんな名前のファイルは無いと言われたわけです。`sudo sh -c '...'` で囲めば、展開もrootで行われます。

### ローテートが止まっていた

ログディレクトリの更新日時は3月で止まっていました。前回のローテートで作られた非圧縮のファイルも残ったままです。`delaycompress` は「前回のファイルの圧縮を次のローテートまで延期する」指定なので（logrotate, 2026a）、次の回が来ていないことを示しています。別CMSのプロファイルにいたっては、作成以来一度も回っていませんでした。

### 手動では動く、夜間は動かない

`sudo logrotate -d`（変更を加えないデバッグ実行）では、両プロファイルのログを認識して回そうとします。上流のlogrotate.serviceには「userdirのログのためProtectHomeを付けない」というコメントがあり（logrotate, 2026b）、systemdの保護設定でホームが見えないわけでもありません。

そこで実行コンテキスト（SELinux上でプロセスがどのドメインで動くか）の差を疑いました。logrotateは実行ファイルの型 `logrotate_exec_t` を入口にlogrotate_tドメインで動きます（Fedora Project, 2026）。sudoで手動実行した側が同じドメインで動いていたかは確かめていませんが、結果が違う以上、別の文脈で動いていると考えました。`ausearch` で確かめると、毎晩00:00:01にAVC（SELinuxの拒否記録）が出ていました。要点だけを抜き出すと次のとおりです。

```text
avc: denied { read } for comm="logrotate" name="nginx"
  scontext=system_u:system_r:logrotate_t:s0
  tcontext=...:object_r:user_home_t:s0 tclass=dir
```

拒否されていたのは、WordPressのプロファイルにある `nginx`・`httpd` ディレクトリの読み取りです。ここのラベルは `user_home_t` でした。別CMSのプロファイルは、過去に私が足した `semanage fcontext` のルールで `var_log_t` になっていました。logrotate_tのポリシー文書を見ると、管理できるファイルの型として「logfile（すべてのログファイル）」は挙がっていますが、`user_home_t` はありません（Fedora Project, 2026）。

### 1件の拒否がグロブ全体を黙らせる

不思議なのは、ラベルが正しかった別CMSのプロファイルも回っていなかったことです。logrotateのソースを読むと、理由が分かりました。

logrotateは設定のパスを `glob(3)` で展開し、エラー時のコールバックでENOENTとENOTDIR以外を受けると1を返して展開を中断させます（logrotate, 2026c）。`glob(3)` はコールバックが非ゼロを返すとそこで終了します（Linux man-pages project, 2026）。中断された場合、`missingok` があればそのパターンを丸ごと読み飛ばし、エラーメッセージも出しません（logrotate, 2026c）。3.18.0タグのソースでも同じ処理です。

つまり、`/home/kusanagi/*/log/nginx/*.log` のどこか1か所で読み取りが拒否されると、正しくラベル付けされたプロファイルも含めて、パターン全体が対象外になります。終了コードは成功のままです。別CMSのプロファイルが「作成以来一度も回っていない」のは、この挙動と合います。ただし、正常側が3月に一度だけ回った理由と、それ以前の空白の理由は確認できていません。

### 対処：ラベルをパターンで管理する

漏れの原因は、プロファイルを足すたびに個別のルールを足してきたことだと考えています。汎用のルールに置き換えました。

```sh
semanage fcontext -a -t var_log_t '/home/kusanagi/[^/]+/log(/.*)?'
restorecon -Rv /home/kusanagi
```

`semanage fcontext` はポリシー側の定義を変えるだけで、実際のラベルは `restorecon` で反映されます（SELinux Project, 2026a, 2026b）。なお、`semanage fcontext` で足したローカルのルールは「新しいものから順に、最初に一致したもの」が使われ、最も具体的なものが選ばれるわけではありません（SELinux Project, 2026a）。今回は既存のルールも同じ `var_log_t` なので結果は変わりませんが、型の違うルールを重ねるときは注意が要ります。

確認は夜間と同じ条件、つまり `systemctl start logrotate.service` で行いました。AVCは出ず、両プロファイルに日付付きのファイルができました。ローテート直後のログは0バイトなので、curlで1リクエスト送り、新しいファイルに書き込まれることまで確かめています。

```sh
systemctl start logrotate.service
ausearch -m AVC -c logrotate -ts recent
```

本稿の時点で確かめたのはこの手動起動までです。翌日以降の夜間実行は `ausearch -m AVC -c logrotate -ts today` で見ていきます。

## 実践への応用・考察

1つ目は、`missingok` の意味です。名前は「ファイルが無くてもよい」ですが、実装上はグロブの展開失敗も黙って飲み込みます。ホーム配下のように権限やラベルが揺れやすい場所をグロブで指定するなら、`missingok` は失敗を隠す側に働きます。ローテート後のファイルの日付を定期的に見るなど、成功終了とは別の確認手段が必要だと私は考えています。

2つ目は、確認の条件です。「sudoで手で実行したら動いた」は、本番の実行コンテキストでの確認になっていません。SELinux環境では、systemd経由とログインシェル経由でドメインが違います。夜間のジョブは `systemctl start` で同じ経路から起動して確かめるべきでした。

3つ目は、自分の過去記事との関係です。「[KUSANAGIにWinter CMSを相乗りさせる](/blog/2026-08-24-kusanagiにwinter-cmsを相乗りさせるwordpress専用ディストリで別cmsを本番稼働させるまで/)」で、`chcon` は一時的で恒久化は `semanage fcontext` と書きました。その恒久化をプロファイル単位で行ったことが、今回の漏れにつながっています。SELinuxを切らずにラベルで直す方針は「[CentOS Stream 9でメールサーバーを建てる](/blog/2026-08-16-centos-stream-9でメールサーバーを建てるselinuxを切らずにmail-tester-10-10へ/)」から変えていません。変えるべきは、ルールの粒度でした。

## まとめ

- 00:00のPermission deniedは、ログディレクトリの754でワーカーがログを開き直せなかったため
- ローテートの停止は、logrotate_tが `user_home_t` のディレクトリを読めなかったため
- logrotateはグロブ展開中のエラー1件でパターン全体を捨て、`missingok` があれば何も出さずに成功終了する
- 手動実行ではなく、`systemctl start` で本番と同じ実行コンテキストから確かめる
- SELinuxのラベルはプロファイル単位ではなく、パスのパターンで管理する

ホーム配下のログをlogrotateで回している方は、ローテート済みファイルの日付と `ausearch -m AVC -c logrotate` の結果を一度確認してみてください。
