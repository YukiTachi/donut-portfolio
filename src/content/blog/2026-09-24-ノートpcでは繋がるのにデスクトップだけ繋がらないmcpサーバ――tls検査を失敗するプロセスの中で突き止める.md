## はじめに

設定ファイルは同じ。トークンも同じ。サーバも同じ。なのに、ノートPCでは繋がるMCP（Model Context Protocol）サーバが、デスクトップPCからだけ繋がらない――2026年9月下旬に筆者が踏んだ事象です。

MCPクライアントが出すのは「タイムアウト」「Connection closed」という結果だけで、原因の層を教えてくれません。本記事は、その表示の下にある本当の失敗地点をどう観測したかの実録です。真因は常駐セキュリティソフトによるTLS検査で、決め手は「失敗するプロセスの中にスクリプトを置く」ことでした。「[MCPサーバの認証設計](/blog/2026-08-22-mcpサーバの認証設計固定bearerからoauth-2-1へjwt検証でステートレスに保つ/)」「[Let's Encrypt証明書のトラブルシュート実践](/blog/2026-08-02-lets-encrypt証明書のトラブルシュート実践メール証明書エラー1件から自動更新の設計不備を洗い出す/)」に続く、証明書まわりの切り分け編です。プロダクト名・実ドメイン・トークンは伏せて書きます。

## 背景・課題

構成はこうです。Claude DesktopがMCPサーバを起動するとき、設定ファイルで指定できるのは `command` と `args` による子プロセス、つまりstdio型のサーバです（Model Context Protocol, 2026）。リモートのHTTPサーバへ繋ぐには、その橋渡しを挟みます。

```text
Claude Desktop → cmd.exe → npx → mcp-remote → リモートMCPサーバ（Bearer認証）
```

見落としやすいのは、`npx` が起動のたびにパッケージをレジストリから取得しうる点です。MCPの接続には、MCPとは無関係のHTTPS通信が前段に潜んでいます。

ログの所在は公式に決まっていて、Windowsなら `%APPDATA%\Claude\logs`、macOSなら `~/Library/Logs/Claude` に `mcp*.log` が書かれます。ここには接続イベント、設定の問題、実行時エラー、メッセージ交換が記録されます（Model Context Protocol, 2026）。

2台の差分はハードウェアと常駐ソフトだけ。設定ファイルはバイト単位で同一でした。

## 本論

### ログを読む――タイムアウトの行間に別のエラーがある

MCPログを追うと、目立つのは `initialize` のタイムアウトと切断です。しかしその間に、MCPとは語彙の違う行が混ざっていました。

```text
npm error code UNABLE_TO_VERIFY_LEAF_SIGNATURE
npm error request to https://registry.npmjs.org/... failed,
  reason: unable to verify the first certificate
```

これはMCPの失敗ではなく、npxがパッケージを取りに行く段階の失敗です。`UNABLE_TO_VERIFY_LEAF_SIGNATURE` はNode.jsが返すOpenSSLのエラーコードで、意味は「最初の証明書を検証できない」です（Node.js, 2026b）。

npmのデバッグログからは、実際に使われたNode（nvm管理の v22.11.0）、作業ディレクトリ（`C:\Windows\System32`）、読み込まれたnpmrcの一覧が取れました。作業ディレクトリがSystem32なのは偶然ではなく、クライアント経由で起動されたstdioサーバの作業ディレクトリは未定義になりうる、と公式が明示しています（Model Context Protocol, 2026）。npmは設定をプロジェクト／ユーザー／グローバル／組み込みの4ファイルから優先順に解決します（npm, 2026b）。プロジェクトの位置は、作業ディレクトリから親をたどって `package.json` か `node_modules` を探し、見つからなければ作業ディレクトリそのものになります（npm, 2026c）。結果、`System32\.npmrc` がプロジェクト設定として探索されていました（ファイル自体は存在しません）。

### 消去法――外から条件を揃えても再現しない

最初に立てた仮説は、プロキシ設定かnpm設定でした。順に潰します。

- PowerShellから `npm view` は成功。Nodeの `https.get` も200を返す
- 同じ `node.exe`、同じ作業ディレクトリ（System32）に揃えても成功
- npmrc 4か所のうち実在したのはユーザー設定の1つだけで、中身は `strict-ssl=true` のみ。これは既定値そのものです（npm, 2026a）
- 設定ファイルの `env` に入っているのは認証ヘッダだけ（`env` キーの用途は公式どおり：Model Context Protocol, 2026）

仮説は全滅し、残るのは「Claude Desktopから起動されたプロセスに固有の何か」という一点です。裏を返すと、**外から条件を揃える方法では原理的に捕まえられない**ということでもあります。

### 核心――失敗するプロセスの中に観測点を置く

そこで観測点を移しました。診断スクリプトを書き、それを**ダミーのMCPサーバとしてClaude Desktopに起動させます**。MCPを話さないのでクライアント上はエラー表示になりますが、出力したファイルは残ります。

```javascript
// diag.js: 失敗する実行環境の中から、相手が出した証明書チェーンを取り出す
const tls = require('tls');
const s = tls.connect(
  { host: 'registry.npmjs.org', port: 443, servername: 'registry.npmjs.org',
    rejectUnauthorized: false },   // 検証を通さず「誰が出したか」だけを見る
  () => {
    let c = s.getPeerCertificate(true);   // true でチェーン全体
    while (c) {
      console.log('subject:', c.subject.CN, '/ issuer:', c.issuer.CN);
      c = (c.issuerCertificate === c) ? null : c.issuerCertificate;
    }
    console.log('authorized:', s.authorized, s.authorizationError);
    s.end();
  }
);
```

`rejectUnauthorized` は既定で `true` で、検証に失敗すると `err.code` にOpenSSLのエラーコードが入ります。`getPeerCertificate(true)` は各証明書に `issuerCertificate` を付けた完全なチェーンを返します（Node.js, 2026b）。ここでは検証を通すことが目的ではないので、あえて `false` にして発行元だけを見ます。

結果は明快でした。

| 起動経路 | node | チェーン | authorized |
|---|---|---|---|
| PowerShell | v20.18.1 | Google Trust Services WE1 → GTS Root R4 → GlobalSign Root CA | true |
| Claude Desktop | v22.11.0 | Norton Web/Mail Shield Root | false（`UNABLE_TO_VERIFY_LEAF_SIGNATURE`） |

表の2行はnodeのバージョンも違います。ただし消去法の段階で、v22.11.0 のnpmをPowerShellから実行して成功しているので、この差はバージョンでは説明できません。

証明書ストアで該当のルートを確認すると、OU欄に `generated by Norton Antivirus for SSL/TLS scanning` とありました。npmもアプリも「検証に失敗した」という結果しか残さないので、**発行元はこの方法でしか見えませんでした**。

### なぜNodeだけが失敗するのか

セキュリティソフトのTLS検査は、自分のルート証明書をOSの証明書ストアに入れ、通信の証明書を差し替えます。OSストアを参照するブラウザなどは差し替え後の証明書を信頼するので、何も起きません。

一方、Node.jsは既定でMozilla由来の同梱ルートCAを使い、OSのストアを参照しません（Node.js, 2026a）。だから「ブラウザは通るのにNodeだけ失敗する」という非対称が生まれます。

なお、OSのストアを使わせる `--use-system-ca` / `NODE_USE_SYSTEM_CA=1` が使えるのは v22.19.0・v24.6.0 以降です（Node.js, 2026a）。今回の v22.11.0 では使えません。ちなみに現行のNodeは、この種の証明書エラーが出たときに `--use-system-ca` を案内するヒントを自動で添えます（Node.js, 2026b）。

### 対処――除外設定と、その代替

採った対処は、セキュリティソフト側の除外にnpmレジストリとMCPサーバのドメインを追加することでした。入力するとhttp/https両方と `/*` に自動展開され、再起動後に接続成功を確認しています。

Nortonの公式資料で確認できたのは、HTTPS検査が「暗号化されたトラフィックを復号してスキャンする」こと、除外タブで「Don't scan（スキャンしない）」を選べることまでです（NortonLifeLock, 2024）。この記述はMac版Safe Webのページのもので、Windows版のUI名称はバージョンにより異なります。「除外追加＝TLS検査の対象外化」という公式の説明は見つけられませんでした。よって**除外追加後に接続成功を確認したという実測**としてのみ扱います。

代替は `NODE_EXTRA_CA_CERTS` に当該ルートをPEMで置く方法です（Node.js, 2026a）。確実ですが、ルート証明書が更新されるたびに再出力が要ります。`strict-ssl=false` は原因を確かめないまま検証そのものを切る操作なので、採りませんでした。最後に、診断用のエントリと出力ファイルは片付けます。

## 実践への応用・考察

持ち帰れるのは3点です。

**1. 外から再現しないなら、失敗する実行環境の中に観測点を置く**。条件を外から揃える試みはすべて成功してしまい、かえって範囲が絞れました。決め手は、診断スクリプトを起動される側として登録する発想の転換です。MCPに限らず、エディタ拡張・CI・サービスマネージャ経由で動くプロセス全般に効きます。

**2. TLSの失敗では「誰が証明書を出しているか」を見る**。検証エラーの文字列は結果でしかありません。`rejectUnauthorized: false` はプロダクションでは危険ですが、診断目的で発行元を見るだけなら数行で答えが出ます。

**3. 「同じ設定」は環境が同じことを意味しない**。設定ファイルをバイト単位で揃えても、常駐ソフトという層は残ります。筆者の経験では、この層は設定の差分検査では絶対に出てきません。

未解明の点も残っています。同じ v22.11.0 の `node.exe` でも、PowerShellから起動したときは検査されませんでした。判定条件は確認できていないので、「起動のされ方によって扱いが変わるように見える」以上のことは書けません。

副次的な気づきをひとつ。診断用のバッチで、括弧ブロック内に日付・時刻を展開する行を置いたところ、構文エラーでファイル自体が作られませんでした。原因は未検証で、対処は「括弧ブロック内での展開を避けた」だけです。

## まとめ

- MCPクライアントの「タイムアウト」「切断」は結果の表示。`%APPDATA%\Claude\logs` のログを、MCP以外の語彙が混ざっていないかという目で読む
- `npx` 経由の構成では、MCPの前段にnpmレジストリへのHTTPSが挟まる。そこが失敗しても症状はMCPの接続失敗に見える
- 外から条件を揃えても再現しないときは、診断スクリプトをダミーのMCPサーバとして登録し、失敗するプロセスの中で観測する
- TLS検証の失敗は `getPeerCertificate(true)` でチェーンのissuerを見れば原因がほぼ確定する
- Node.jsは既定でOSの証明書ストアを参照しない。OSストアを使うなら v22.19.0・v24.6.0 以降の `--use-system-ca`、それ以前なら `NODE_EXTRA_CA_CERTS`

次に手を動かすなら、繋がらない側のログから「MCPの語彙ではない行」を探すところからです。層が1つ下りれば、容疑者は一気に減ります。
