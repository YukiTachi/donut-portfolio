# BrainSync ブログ記事 自動生成タスク(cron 非対話実行 / WordPress)

あなたは cron から **非対話モード(`claude --print`)** で起動された Claude Code です。
ユーザーへの問い返しはできません。判断は自分で行い、最後に**機械可読なサマリーブロック**を必ず出力してください。

対象サイトは **donut-service.com(WordPress)** です。Astro の `donut-portfolio` とは別サイトなので、
`src/content/blog/` への保存・git commit・push は**一切行いません**。

## 対象リソース

- Notion ページ「BrainSyncブログ」: `3aad745d-3f83-81f9-b95f-f2a2f656ed4c`
- WordPress MCP: `donut-wp`(Bearer トークン認証 / Access Level: Read-Write (Content))

## 最も重要な原則

**このタスクは記事を公開しません。** 必ず `post_status: draft` で投入し、公開は人間が判断します。
どのような場合でも `publish` / `future` / `pending` を指定してはいけません。

## 処理手順

1. **WordPress 疎通確認**: 最初に `mcp_ping` を実行し、WordPress MCP に到達できることを確認する。
   - 失敗したら **Notion には一切触れず**、`RESULT=ERROR` / `ERROR_PHASE=wp_connect` を出力して終了する。
   - Notion 操作の前に確認するのは、ロールバックを不要にするため。

2. **ネタ取得**: Notion MCP で「BrainSyncブログ」ページを**上記「対象リソース」の固定ページID(`3aad745d-3f83-81f9-b95f-f2a2f656ed4c`)で取得**し、`## 未処理` セクションの**最上行(箇条書き 1 件)**を処理対象として抜き出す。
   - **必ずこのページIDで取得すること**。タイトルでの検索はしない(ページタイトルは変更されることがある)。
   - 行に `📝 メモ` トグルが付いていれば、その内容(狙い・骨子の芯・検証が要る論点)を執筆の指針として必ず読む。
   - 「未処理」が空なら、何も生成せず `RESULT=SKIP` を出力して終了する。

3. **処理中へ移動**: 対象の行を Notion 上で `## 未処理` から `## 処理中` へ移動する。
   - Notion の更新は、必ず**先にページを取得して正確な文字列を得てから**行う(自動リンク化で URL が変化するため)。
   - `<details>` トグルのインデントはタブで、マーカー行が 1 タブ、内容が 2 タブ。崩さないこと。

4. **エビデンス収集**: Web 検索でテーマに応じた論文・一次資料・統計を収集する。
   BrainSync 系の記事は健康・認知に関する主張を含むため、以下を**厳守**する。

   - 書誌情報(著者・年・掲載誌・巻号・ページ・DOI)は、実際に検索して確認したものだけを書く。
     確認できないものは書かず、どうしても言及が必要なら `[要確認]` を付ける。
   - **各研究について「結論の向き」まで確認する。** 書誌情報が正しく、引用が逐語一致していても、
     結論の向きを取り違える誤りが実際に発生している。要旨を読み、その研究が主張を
     **支持しているのか否定しているのか**を判定したうえで本文に配置する。
     - 実例(2026-07-26, 投稿 ID 132): Du ら(2020)を「質の高い研究ほど効果が小さい」と要約したが、
       実際は「質の高い研究群でも高次の意思決定への影響は残る」であり向きが逆だった。
     - 実例(同上): Fan ら(2023)のメタ解析を「反対側の証拠」節に配置したが、結論は影響を支持する側だった。
   - 知見が割れているテーマでは、**必ず両論併記**する。片側だけを引いて断定しない。
   - 「◯◯すれば生産性が上がる」式の効果を誇張しない。効果量の不確かさは正直に書く。

5. **既存記事のトーン確認**: `wp_get_posts` で公開済み記事を一覧し、直近の 2〜3 本を `wp_get_post`
   (`content_format: prose`)で読んで、文体・構成・見出し番号の付け方・CTA の位置を揃える。

6. **記事生成**: 以下の構成・形式に従う。

   - **形式**: Gutenberg ブロック。段落は `<!-- wp:paragraph -->`、見出しは `<!-- wp:heading -->` で囲む。
     ブロックコメントの対応が崩れると管理画面でブロック検証エラーになる。
   - **構成**: 冒頭の日付署名行 → 導入 → 番号付き H2 セクション(H3 は `2-1` のように親番号を継ぐ)
     → まとめ → BrainSync の CTA → 参考文献 → 関連記事。区切り線(`<!-- wp:separator -->`)で節を分ける。
   - **分量**: 3,000〜4,000 字程度。
   - **コード・コマンド名**: 必ず `<code>` を使う。`<strong>` で代用しない
     (2026-07-26 に `<code>i2cdetect</code>` が `<strong>` に置き換わる事故が発生している)。
   - **内部リンク**: 関連する既存記事へ本文中から 2〜3 本張る。URL は `wp_get_posts` で得た実 permalink を使い、
     推測で組み立てない。
   - **健康に関する記述**: 診断的な書き方をしない。症状に触れる場合は受診を勧める一文を添える。
     末尾に「効果には個人差があります。本記事は医療助言ではありません。」を必ず入れる。
   - **プレースホルダ**: 裏取りできなかった事実には `[要確認：内容]`、筆者の一次データが必要な箇所には
     `[実測データ挿入：挿入すべき内容]` を置く。**捏造で埋めない。**
   - `post_excerpt` も生成する。

7. **自己レビュー**: 保存前に以下を 1 項目ずつ `[OK]` / `[FIX]` で判定する。`[FIX]` があれば直して再判定し、
   **全項目が `[OK]` になるまで投稿しない**。文字数や出典件数など客観的に数えられるものは実際に数える。

   - [ ] 引用したすべての研究について、書誌情報を検索で確認した
   - [ ] 引用したすべての研究について、結論の向き(支持/否定)を要旨で確認し、本文の配置と一致している
   - [ ] 知見が割れているテーマで、片側だけを引いていない
   - [ ] 引用符で囲んだ箇所は原文と逐語一致している(切り詰めていない)
   - [ ] 出典より踏み込んだ断定をしていない(出典が「5.x」なら本文も「5.x」)
   - [ ] Gutenberg ブロックコメントの対応が取れている
   - [ ] コマンド名・コードは `<code>` で囲まれている
   - [ ] 内部リンクの URL は実在の permalink である
   - [ ] 医療助言に読める記述がない。免責の一文がある
   - [ ] 本文の文字数が 3,000〜4,000 字の範囲にある

8. **WordPress へ投稿**: `wp_create_post` で投入する。
   - `post_status` は **必ず `"draft"`**。
   - 返却された投稿 ID を記録する。以降の工程で失敗した場合、この ID を `ORPHAN_POST_ID` として報告する。

9. **カテゴリー・タグ付与**: `wp_add_post_terms` で設定する。
   - **カテゴリー**: `wp_get_terms`(taxonomy=`category`)で既存を取得し、その中から選ぶ。
     `3`(エンジニアのウェルビーイング)は必ず含める。**カテゴリーを新規作成してはいけない**(人間の判断が必要)。
     投稿後に `wp_get_post_terms` で「未分類」(term_id 1)が残っていないか確認し、残っていれば外す。
   - **タグ**: 既存タグを優先する。`wp_get_terms`(taxonomy=`post_tag`)で一覧を取得し、意味が重なるものは再利用する。
     - 新規作成は**最大 2 件まで**。作成前に `search` で重複(表記ゆれ・英日の別表記)を必ず確認する。
     - **記事タイトルや長いフレーズをタグにしない。** 過去にタイトルがそのままタグ化された事故がある。
     - 合計 6〜8 件を目安とする。

10. **Notion 更新**: 対象行は `## 処理中` に**残したまま**、行末に `（投稿ID {ID} / draft）` を追記し、
    その下に `📋 公開前チェックリスト` の `<details>` トグルを追加する。中身は以下の 3 ブロック。

    - **出典の裏取り(完了)**: 確認できた文献を `- [x]` で列挙(著者・年・掲載誌・巻号・ページ)。
      結論の向きも 1 行で添える。
    - **残タスク(公開前に必要)**: `[要確認]` / `[実測データ挿入]` の各箇所、アイキャッチ未設定などを `- [ ]` で列挙。
    - **申し送り**: 生成中に気づいた注意点があれば記載。

    **`## 完了` へは移動しない。** 完了は人間が記事を公開したときに手で移す。
    公開時のエントリ形式は `- YYYY-MM-DD HH:MM | {タイトル} → {permalink}`。

## エラー時の扱い

- いずれかの工程で続行不能な失敗が起きたら、可能なら Notion の対象行を `## 処理中` → `## 未処理` に戻し、
  `- {元のネタテキスト} [前回失敗: YYYY-MM-DD, {エラー概要}]` の形式でエラーメモを付ける。
  `📝 メモ` トグルが付いていた場合は一緒に戻すこと(失わない)。
- `wp_create_post` が成功した後に失敗した場合、**下書きは削除しない**。`ORPHAN_POST_ID` に投稿 ID を入れて報告し、
  人間が判断できるようにする。
- そのうえで `RESULT=ERROR` のサマリーを出力して終了する。
- 投稿まで成功したが Notion 更新だけ失敗した場合は、**成功扱い**とし、`RESULT=SUCCESS` かつ `NOTION=FAILED` を出力する。

## 出力契約(最重要)

処理の最後に、**必ず**以下のマーカーで囲んだサマリーブロックを**標準出力**へ出力すること。
シェルスクリプトがこのブロックだけを抽出してメール通知に使う。各行は `KEY=VALUE` 形式、1 行 1 項目、余計な装飾を付けない。

### 成功時

```
===BLOG_CRON_RESULT_BEGIN===
RESULT=SUCCESS
TITLE={記事タイトル}
POST_ID={WordPress の投稿ID}
POST_STATUS=draft
CHARS={本文の概算文字数}
CATEGORIES={カテゴリー名をカンマ区切り}
TAGS={タグ名をカンマ区切り}
TOPIC={元ネタのテキスト}
EVIDENCE_PAPER={学術論文の参照件数}
EVIDENCE_OFFICIAL={公式ドキュメントの件数}
EVIDENCE_GOV={政府・公的資料の件数}
EVIDENCE_WEB={Web記事の件数}
PLACEHOLDER_TODO={本文に残した [要確認] の件数}
PLACEHOLDER_DATA={本文に残した [実測データ挿入] の件数}
NOTION={OK または FAILED}
===BLOG_CRON_RESULT_END===
```

### スキップ時(未処理ネタなし)

```
===BLOG_CRON_RESULT_BEGIN===
RESULT=SKIP
MESSAGE={スキップ理由の簡潔な説明}
===BLOG_CRON_RESULT_END===
```

### 失敗時

```
===BLOG_CRON_RESULT_BEGIN===
RESULT=ERROR
ERROR_PHASE={topic_fetch | research | generation | format_check | wp_connect | wp_create | notion_update のいずれか}
ERROR={エラー概要を1行で}
TOPIC={判明していれば元ネタ、不明なら空}
NOTION_RESTORED={OK または FAILED — 対象行を未処理に戻せたか}
ORPHAN_POST_ID={下書きが残っていればその投稿ID、無ければ空}
===BLOG_CRON_RESULT_END===
```

### 注意

- サマリーブロックは**1 回だけ**、処理の最後に出力する。
- `POST_STATUS` は `draft` 以外を出力してはいけない。シェル側は `draft` 以外を検出すると
  「意図しない公開の可能性あり」として失敗扱いにする。
- `RESULT=SUCCESS` を出すときは `POST_ID` を必ず埋める。空だとシェル側で失敗扱いになる。
- `PLACEHOLDER_TODO` / `PLACEHOLDER_DATA` は 0 でも省略せず `0` と書く。
- 値に改行を含めない(タイトルやメッセージは 1 行に収める)。タイトルにカンマを含めてよいが、
  `CATEGORIES` と `TAGS` のみカンマ区切りである点に注意。
